CEO demo for Deborah Michals

A working chaperone app for safer, more visible rides.

This demo walks through what a TrustedRiders chaperone can do today: sign in, see assigned rides, launch navigation, check off mission milestones, chat with dispatch, escalate emergencies, and communicate operational updates back to the backend.

End-to-end system

The app is no longer an isolated prototype.

The mobile app is wired around the real operating loop: authenticated chaperone actions, Fleet API ride data, foreground/background location pings, and chat-style mission events that dispatch can consume.

AuthenticationChaperones sign in against the backend and the app stores the session token.
Ride dataRide lists and ride details hydrate the current ride, request detail, routes, notes, and contact fields.
Simulation proofWe created and ran a simulation system with 5 parallel simulated rides executing and being live tracked.

Chaperone home

The current ride is immediately understandable.

Deborah can see the product promise in one screen: who the rider is, where the pickup/drop-off are, when pickup starts, what care notes matter, and whether the chaperone is live.

Backend proofThe screen is hydrated by ride payloads: route coordinates, rider identity, scheduled time, notes, phone numbers, and status.

New assignment

A chaperone can review, accept, or decline a ride request.

Pending assignments are shown with the route, rider context, care notes, pickup/drop-off, and clear action buttons. This is the first major handoff from dispatch into the mobile workflow.

Feature highlightChaperone sees the job before committing, including medical/care context and route geography.
Backend follow-upAccept/decline needs final live endpoint verification and status reconciliation with dispatch.

Mission execution

Checkpoint details make each driver update explicit.

During an active mission, the chaperone can review the current step, stop details, next stop, and location metadata before posting an operational update.

Step clarityThe drawer shows the current checkpoint, ride phase, current stop, next stop, and driver coordinates.
Checkpoint modelPickup Passenger, facility drop-off, return pickup, and arrival home keep the ride auditable.
Backend communicationEach checkpoint action can post a mission event through the ride chat path with status, stage, target, and driver location metadata.

Dispatch chat

Chat is both a human channel and a mission event log.

The app includes a dispatch chat surface so the chaperone can message the office about a ride. The mission screen also uses the chat API path to post structured status updates automatically.

Human communicationChaperones can reach dispatch from a ride or active mission context.
Automated backend messagesCheckpoint taps generate structured payloads that include ride id, passenger, current action, next stage, target, and location.
Open workThe screenshot uses mock conversation content; production chat still needs the live backend endpoint completed.

Safety escalation

Emergency actions are one tap away during a mission.

A chaperone can escalate to the rider emergency contact, TrustedRiders dispatch, or 911 from the active mission screen.

Feature highlightThe emergency modal prioritizes clear, high-contrast action choices under stress.
Operational valueDispatch and rider contact details are visible in the moment the chaperone needs them.
Before launchReplace placeholder dispatch phone number and validate exact call routing for production builds.
